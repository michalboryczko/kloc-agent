## Description

After a refresh, the chat history loads user prompts and assistant prose — but tool calls are gone. The screenshot in the bug report shows the live experience (one assistant bubble with `search_code "JWT_SECRET"`, `read_file JwtFactory.php`, `read_file .env DENIED` stacked above the prose); after F5 the same session reloads with only the prose. The tool cards never come back.

Root cause: tool-call events are NEVER PERSISTED. They only ever live in `ExecutionRegistry`'s in-memory ring (10k events, ~5 min eviction). `_persist_events` (`src/api/stream.py:224-323`) explicitly handles only `TEXT_MESSAGE_CONTENT` and `TEXT_MESSAGE_END`. On reload, `GET /v1/sessions/{id}/messages` returns rows from the `messages` table that contain only `content` text — no tool metadata exists in the database to return. The frontend's `persistedToMessageView` (`frontend/src/lib/reducer.ts:24-35`) hardcodes `toolCalls: []` because the wire shape has no field to populate from.

T06 makes tool calls durable. The persistence model:

### Schema choice — separate `tool_calls` table, NOT `content_parts` JSONB

Two options were considered:

**Option A — extend `messages.content_parts` JSONB with a `tool_calls: [...]` array.**
- Pros: no new table, one migration is trivial.
- Cons: tool-call rows mutate over the run lifecycle (start → args delta → end → result). Mutating a JSONB array under concurrent SSE delivery requires read-modify-write with optimistic locking (or `jsonb_set` per delta). Bulk reads of "all tool calls in a session" require iterating every message row's JSONB. Indexing on `tool_call_id` for de-dup is awkward.

**Option B — a new `tool_calls` table with `parent_message_id` FK.** ← chosen
- Pros: per-tool-call row is a stable identity. `tool_call_id` is the natural PK (deduplicated implicitly via `ON CONFLICT DO UPDATE`). State transitions (running → done → denied) are simple `UPDATE` statements. Result-bearing columns can be `TEXT` (with size cap reusing T02's policy) or pointer-to-artifact rows for offloaded results. Cross-session analytics (e.g. "tools most frequently denied") becomes a single-table query.
- Cons: one extra join in the read path. Mitigated by adding `tool_calls` as a one-shot SELECT keyed by `session_id` and merging in Python — same cost as the JSONB iterate-in-memory approach.

The persistence layer therefore gains one new table, one new repo (`ToolCallRepo`), and one new branch in `_persist_events`. The read path joins (`tool_calls` LEFT JOIN `messages` on `parent_message_id`) and groups by `parent_message_id` in Python for the API response.

### `tool_calls` schema

| column | type | nullable | notes |
|---|---|---|---|
| `id` | UUID | NOT NULL PK | server-default `gen_random_uuid()` — the internal row id, distinct from `tool_call_id` |
| `tool_call_id` | TEXT | NOT NULL UNIQUE per session_id | the AG-UI / Strands tool-call id, used to de-dup re-emitted events |
| `session_id` | UUID | NOT NULL FK → `sessions.id` ON DELETE CASCADE | for session-scoped lookups |
| `parent_message_id` | UUID | NOT NULL FK → `messages.id` ON DELETE CASCADE | the assistant message this tool call belongs to (provided by T05) |
| `tool_name` | TEXT | NOT NULL | e.g. `kloc_search_code`, `kloc_read_file` |
| `args` | TEXT | NOT NULL DEFAULT `''` | accumulated `TOOL_CALL_ARGS` delta chunks |
| `result` | TEXT | NULL | populated on `TOOL_CALL_RESULT`; size-capped per T02 policy (reuse `KLOC_TOOL_LIMITS.result_max_bytes`); large results go to an artifact row and `result` holds a pointer comment |
| `state` | TEXT | NOT NULL | `'running' | 'done' | 'denied'` enum-typed via `CHECK` constraint |
| `denied_reason` | TEXT | NULL | populated when `state = 'denied'`, from `ToolCallDenied.value.reason` |
| `denied_hint` | TEXT | NULL | populated when `state = 'denied'` and a hint is provided |
| `seq` | BIGINT | NOT NULL | per-(session_id, parent_message_id) ordering; assigned at insert; allows the UI to render tool cards in the same order they fired |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT `now()` | when `TOOL_CALL_START` landed |
| `finalized_at` | TIMESTAMPTZ | NULL | when `TOOL_CALL_END` or `ToolCallDenied` landed |

Indexes:
- PK `tool_calls_pkey` on `id`.
- UNIQUE `uq_tool_calls_session_tool_id` on `(session_id, tool_call_id)` — supports `INSERT ... ON CONFLICT (session_id, tool_call_id) DO UPDATE` for idempotent re-delivery.
- `ix_tool_calls_parent_message` on `parent_message_id` — the API read path's main lookup.
- `ix_tool_calls_session_seq` on `(session_id, seq)` — historical-page hydration.

### Why this depends on T05

`tool_calls.parent_message_id` is `NOT NULL FK → messages.id`. The persister learns the FK target from `TOOL_CALL_START.parentMessageId` (T05's emission contract). Without T05, the persister has no reliable per-event signal to identify the parent; it would have to derive parent from "the most recent assistant row written in this run" — a heuristic that breaks when the runner emits multiple text-blocks-with-interleaved-tool-calls in a single turn. T05's invariant makes the FK a direct lookup, not a guess.

### Out of scope for T06

- **Tool-call retry / re-emission across runs.** If a session resumes after the SSE stream drops mid-turn, the second connection may re-emit `TOOL_CALL_START` for already-persisted tool calls. The `ON CONFLICT (session_id, tool_call_id) DO UPDATE` clause makes this idempotent for `state` and `args` accumulation. Resume semantics across run boundaries are not addressed here.
- **Per-tool-call audit.** Audit rows for `tool_call.started` / `tool_call.completed` / `tool_call.denied` are already written by `src/api/webhooks.py:60-90`. T06 does not touch the audit_log table.
- **Migration of EXISTING sessions' tool-call history.** Pre-T06 sessions have no tool-call data in any persistent store (the in-memory ring evicted it). There is nothing to backfill. Old sessions reload as "prose only" forever; this is acceptable per the bug report (the user wants NEW sessions to round-trip correctly).
- **Pagination of tool calls within a single message.** A single message rarely accumulates >50 tool calls; the API returns all tool calls for the returned message page in one shot. If a future use case demands cursoring inside a message, that's a follow-up.

## Notes

- **Why not embed tool calls inside `messages.content_parts` JSONB:** explained in Description ("Schema choice"). The chosen separate-table design pays a small read-path join cost in exchange for stable per-tool-call identity, idempotent re-emission, and indexable cross-session queries — all of which we want as we grow analytics on tool usage.
- **Truncation choice — open item:** the proposal reuses T02's `KLOC_TOOL_LIMITS.result_max_bytes` for the DB `result` column cap. Alternative: store unbounded result text and rely on the existing artifact-offload path to keep it out of the hot DB row. The artifact-offload alternative is cleaner but doubles the row count for every large result; T06 picks the simpler truncation approach and leaves the offload-pointer option as a follow-up.
- **`seq` column allocation race — open item:** the `seq = MAX(seq) + 1` pattern inside `upsert_started` is racy under concurrent tool-call starts. Mitigations: (a) wrap the insert in a per-session advisory lock, (b) use `INSERT ... RETURNING seq` with a Postgres sequence keyed by `parent_message_id` (requires one sequence per message — wasteful), (c) accept duplicate `seq` values and tie-break by `created_at` in the UI. T06 picks (c) — duplicate seq values within one parent are harmless visually because tool-call ordering within a single turn is fine-grained but not safety-critical.
- **Frontend test runner — open question:** the repo today does not appear to have a configured frontend unit-test runner (`package.json` has no `test` script). Deliverable 12's frontend test (`test_persisted_to_message_view.py`) is listed as opt-in; if no test runner is wired during T06 implementation, that test is skipped and the Chrome MCP verification step covers the same surface visually. A separate task can introduce a frontend test runner (vitest + react-testing-library) later.
- **Why not also fix old in-memory-only sessions:** the ExecutionRegistry ring has no durable backing. There is no data to recover for pre-T06 sessions. Acceptable behaviour: old sessions show prose-only on reload; new sessions show full history.
- **Webhook + persister race:** `src/api/webhooks.py` writes audit_log rows for `tool_call.started` / `tool_call.completed` / `tool_call.denied`. `_persist_events` writes `tool_calls` rows. The two paths are independent — webhook handles audit; persister handles UI-restorable state. No coordination needed between them.
