## Description

Today the orchestrator has three bad options when an analyst asks "show me line 42 of `src/Order/OrderFactory.php`":

1. `kloc_source` / `kloc_chunks` — works for indexed PHP, but loses non-PHP files (YAML, XML, JSON, MD) and loses byte-exact ranges (chunker may not align with the requested line).
2. `file_read` — works for arbitrary paths the runner has access to, but the runner image has NO project source mounted, so it currently resolves nothing useful. If we naively bound a wide path, `file_read` would happily walk the entire host filesystem because nothing scopes it.
3. Give up on file:line citations — violates the base_prompt's "Hard rules" discipline.

T09 closes the gap. Two ships, one task:

### Part 1 — the `kloc-projects` named volume

- Add a `projects-init` sidecar to `docker-compose.yml`, modelled byte-for-byte on `skills-init` / `agents-init`. Seeds `kloc-projects` from the repo-root `./projects/` on first boot.
- Add the `kloc-projects` named volume entry to the `volumes:` block of `docker-compose.yml`.
- Add `build_projects_mount()` in `src/runner_mgmt/hydrate.py`, returning the aiodocker dict `{"Type": "volume", "Source": os.environ.get("KLOC_PROJECTS_VOLUME", "kloc-projects"), "Target": "/projects", "ReadOnly": True}`. Lazy env-read for parity with the existing helpers.
- Append `build_projects_mount()` to `HostConfig.Mounts` in `src/runner_mgmt/docker_runner.py:144-148`. The runner now sees four mounts in this order: hydration, skills, agents, projects.
- Add `projects_dir: str = "/projects"` to `HydrationPayload` in `src/db/models.py`. The backend's hydration writer passes the field; the runner's tool consults it for path resolution.
- Add `backend` service mount in `docker-compose.yml`: `- kloc-projects:/projects-source:ro` (paralleling `kloc-skills:/skills-source:ro` at line 151). This makes the seeded volume readable inside the backend for tests / introspection / Step 8 of verification (the smoke script reads `/projects-source` to confirm the seed worked).
- Add `backend` `depends_on` entry: `projects-init: condition: service_completed_successfully`. Without it the backend may attempt to spawn a runner before the volume is seeded.

### Part 2 — the `read_project_file` Strands tool

- New file `runner/tools/__init__.py` (empty `from __future__ import annotations` line plus module docstring), `runner/tools/project_files.py` containing the `@tool`-decorated `read_project_file(project_name: str, path: str, start_line: int | None = None, end_line: int | None = None) -> str`.
- Schema + behaviour follow AC5–AC14 in `docs/specs/runner-project-files.md`. Summary:
  - `project_name` regex `^[a-z][a-z0-9-]{0,63}$` — same as `agents_loader._NAME_RE`. Failing match → return `"error: invalid project_name; must match ^[a-z][a-z0-9-]*$"` (NO filesystem call).
  - Path resolution via `Path(projects_dir, project_name, path).resolve(strict=True)`. The strict flag makes a symlink to a non-existent target raise (treated as "not a regular file"). Containment check: `str(resolved).startswith(str(project_root_resolved) + os.sep)`. Failing → return `"error: path escapes /projects/{project_name}/"`.
  - Project subdir existence check → `"error: project {project_name} not mounted"` if missing.
  - Regular-file check via `Path.is_file()` (FOLLOWS symlinks, but we already validated the symlink resolution stays in scope) → `"error: not a regular file: {path}"` if directory / FIFO / special.
  - Binary heuristic: read first 8 KiB and attempt `.decode("utf-8")`; on `UnicodeDecodeError` return `"error: file appears to be binary; this tool returns text only"`.
  - Size cap from `settings.tool_limits.read_project_file.max_bytes` (default 256 KiB). When NO line range is requested and `stat().st_size > max_bytes`, the BeforeToolCall policy evaluator denies with `tool_limit:file_too_large` (re-uses the T02 path). When `start_line` / `end_line` ARE requested, the file is read line-by-line via `io.open(...).readlines()` bounded by `end_line`, so a 5 MiB file with a 50-line slice is permitted iff the slice fits the cap.
  - Output: UTF-8 decoded body (or 1-indexed inclusive slice).
- Register `read_project_file` in `runner/agent_factory.py:182-199`:
  - Line ~186-187 (subagent tools): `subagent_tools.append(read_project_file)` immediately after the `file_read` append.
  - Line ~197-199 (orchestrator tools): `tools.append(read_project_file)` likewise.
  - Import: `from .tools.project_files import read_project_file` at the top of `runner/agent_factory.py`. If the import fails (test environment without Strands `@tool` decorator), follow the same try/except pattern used for `from strands_tools import file_read` (graceful skip with a log.warning).
- Policy hook extension in `src/hooks_audit/`:
  - The existing `tool_limit:file_too_large` evaluator extends to `read_project_file` whenever `args["path"]` is provided and the file size exceeds the per-tool cap. The evaluator MAY consult `os.stat()` via `runner/tools/project_files.py:_safe_resolve` (a shared resolver) so it doesn't duplicate the path-traversal check. Implementers can choose: either (a) run the full resolve in the backend evaluator over a path the BACKEND has access to (the backend has `kloc-projects:/projects-source:ro` mounted from the docker-compose change above), or (b) make the policy evaluator inspect `args` only and let the runner-side tool fail with the same hint message if the file is oversized. (b) is simpler and the spec's AC13 only requires the FE sees a `ToolCallDenied` event — either evaluator location works as long as the AG-UI event surfaces the same `tool_limit:file_too_large` reason + hint.
- Settings: add a `ReadProjectFileLimits(BaseModel)` Pydantic submodel with `max_bytes: int | None = 262_144`, and a `read_project_file: ReadProjectFileLimits | None = None` field on `ToolLimitsConfig`. Default cap 256 KiB (matches the spec's open question 1 — "ship at 262144 and re-tune"; mirrors `file_read.max_bytes`).

## Notes
- **Why ship the `kloc-projects` volume + tool together, not in two tasks.** Either alone is dead weight (spec § Problem). A volume with no tool the agent can name reads nothing; a tool with no source mount has nothing to read. Splitting forces a half-shipped intermediate state with zero analyst value.
- **Why a named volume seeded from `./projects/` instead of a bind from `./projects/`.** Same reason as `kloc-skills` / `kloc-agents` already documents at `src/runner_mgmt/hydrate.py:126-130`: aiodocker resolves bind sources host-side, paths inside the backend container don't exist on the host. The named-volume + init-sidecar pattern sidesteps that. Open question 2 in the spec discusses Option B (bind-mount with a CWD-restriction trade-off) — recommendation is to ship Option A and revisit if operators need live source reflection.
- **Why ship `.gitkeep` in `./projects/`.** Operators populate the directory after clone but before `docker compose up`. Without `.gitkeep`, an empty `./projects/` is not in git, and the `projects-init` sidecar's `cp -R /source/. /dest/` fails on a missing source dir. The `.gitkeep` is the minimum viable seed.
- **Why default cap 256 KiB.** Matches `file_read.max_bytes` per `docs/specs/tool-result-size-limits.md:32` AND fits typical Symfony config files (most YAML/XML under 100 KB). Open question 1 in the spec discusses tuning; ship 256 KiB and revisit from real usage.
- **Per-session project allowlist deferred.** `HydrationPayload.allowed_projects: list[str] | None` is mentioned in the spec § "Deferred / out of scope" — single-tenant deployments don't need it. The dev MUST NOT add this field in T09; it lands when a multi-tenant deployment hits the seam.
- **Directory-listing tool deferred.** A sibling `list_project_files` would help the agent discover paths, but every analyst path so far comes back from `kloc_resolve` / `kloc_search` / `kloc_flows`. The dev MUST NOT add this in T09.
- **Symlink-resolved seed semantics.** `./projects/kyc -> /home/me/code/paypo-kyc` is a typical operator pattern. The init sidecar's `cp -R` resolves symlinks and copies contents — "frozen snapshot". README must document this.
- **Cross-tool retire of `file_read` for project paths.** The spec § "Deferred / out of scope" point 5 mentions a future cleanup where `file_read` rejects paths starting with `/projects/`. NOT in scope for T09; the dev MUST leave `file_read` registered alongside `read_project_file`.
