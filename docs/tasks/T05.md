# T05 — tool-call parent linking: group tool calls under their assistant message in the UI

## Status
- pending

## Spec references
- `docs/specs/ui/kloc-analyst.html` — reference design. One `kloc analyst · 14:31` header, followed by a stacked list of `search_code`, `read_file`, `read_file .env DENIED` tool cards, followed by the assistant's prose, followed by an artifact chip. All of it belongs to ONE bubble.
- `frontend/src/components/AssistantBubble.tsx:41-77` — already renders one avatar + header, then `message.toolCalls.map(...)`, then `message.content`, then `message.artifacts.map(...)`. The component structure is correct. The bug is upstream in event ingestion: tool-call events whose `parentMessageId` is missing fall through to a fallback that synthesises a brand-new assistant message instead of attaching to the active one (`frontend/src/lib/reducer.ts:182-219`, specifically the `else` branch at lines 190-198).
- `runner/hooks/audit.py:108-189` — `before_tool_call` and `_emit_tool_call_denied` build webhook + custom-event payloads with `tool_call_id` and `tool_name` but DO NOT carry the active assistant `message_id`. `ArtifactAttached` already does this correctly at line 242-243 (`value["parentMessageId"] = message_id`); tool-call emission must adopt the same pattern.
- `frontend/src/lib/reducer.ts:139-152` — `TEXT_MESSAGE_START` is where the orchestrator's assistant message_id first enters the frontend state. The runner-side equivalent is the AG-UI adapter's `TEXT_MESSAGE_START` emission via `wrap_for_agui` (Strands SDK). The runner therefore already KNOWS the active message_id; it just doesn't thread it into the tool-call hook payloads.
- `docs/usdl/behavior.xml` — `beh.ask-assistant` rule set: a new rule must encode "every tool-call event emitted during an assistant turn carries `parentMessageId` equal to the most-recent `TEXT_MESSAGE_START.messageId` of that turn". Without this invariant the persistence task (T06) cannot correctly attach historical tool calls back to their parent on reload.

## Description

Today the UI renders each tool call as its own top-level assistant message — three tool calls inside one analyst turn produce three "kloc analyst · 14:31" bubbles, not one bubble containing three tool cards. The screenshot in the bug report shows the desired behaviour: a single bubble whose internal layout is `[avatar+header] → [tool cards stacked] → [prose] → [artifact chips]`.

The frontend component (`AssistantBubble.tsx`) already supports this layout — it iterates `message.toolCalls[]` inside one bubble. The data model (`MessageView.toolCalls: ToolCallView[]`, `frontend/src/lib/types.ts:201-210`) is already correct. The bug is in the EVENT INGESTION path:

1. **Runner does not stamp `parentMessageId` on tool-call events.** The Strands AG-UI adapter (`wrap_for_agui`) emits `TEXT_MESSAGE_START` with a fresh `messageId`, but `BeforeToolCallEvent` / `AfterToolCallEvent` audit emissions in `runner/hooks/audit.py` build payloads that omit the parent message id. The synthetic `ToolCallDenied` custom event (`_emit_tool_call_denied`, line 162-189) also omits it. The only path that gets this right today is `ArtifactRegistered → ArtifactAttached` (line 242-243), and we copy that pattern.

2. **Reducer fallback creates a synthetic message when `parentMessageId` is absent.** In `frontend/src/lib/reducer.ts:190-198`:

   ```ts
   } else {
     parentIdx = findOpenAssistantIndex(workingMessages);
     if (parentIdx === -1) {
       const synthetic = makeAssistantMessage(`assistant:${event.toolCallId}`);
       workingMessages = workingMessages.concat(synthetic);
       parentIdx = workingMessages.length - 1;
     }
   }
   ```

   The intent (attach to the most-recent open assistant message via `findOpenAssistantIndex`) is correct, but the synthetic-id branch fires when tool calls arrive BEFORE the first `TEXT_MESSAGE_START` of a turn — and a synthetic message id `assistant:<toolCallId>` will never match a subsequent `TEXT_MESSAGE_START.messageId`, so the assistant's prose lands in a SECOND bubble next to a third tool-call bubble, etc. The user-visible result is the "every tool call is its own message" symptom.

T05 fixes both halves:

### Runner-side: thread the active message_id into tool-call audit emissions

`_AuditHookSender` already holds `_session_id` and `_run_id_provider`. Add an `_active_message_id` field updated by tapping the AG-UI event stream emitted out of the orchestrator (the same stream that emits `TEXT_MESSAGE_START`). The cleanest seam is `runner/agent_factory.py` where `wrap_for_agui(...)` adapts the Strands agent — the wrap layer already knows when `TEXT_MESSAGE_START` fires and can call a setter on the hook sender. Concretely:

- `AuditHookSender` gains `set_active_message_id(message_id: str | None) -> None` and `_active_message_id: str | None = None` (initialised in `__init__`).
- `before_tool_call` (line 108) and `_emit_tool_call_denied` (line 162) include `parentMessageId = self._active_message_id` in the **CUSTOM event value** for `ToolCallDenied` and in the BeforeToolCall webhook payload. The webhook handler in `src/api/webhooks.py:60-90` propagates `parentMessageId` into the AG-UI `TOOL_CALL_START` event published on the event_bus.
- For the BeforeToolCall path that triggers a Strands-native `TOOL_CALL_START` (not a synthetic custom event), the wrap_for_agui layer must inject `parentMessageId` into the AG-UI event before it hits the JSONL frame. Strands's AG-UI adapter exposes the in-flight tool-call event via the hook system; we add a `BeforeAGUIEmitHook` (or equivalent — see `docs/research/02-backend-agui.md`) that mutates the event payload when `event.type == "TOOL_CALL_START"` and `_active_message_id` is set.
- Setter wiring: where `wrap_for_agui` is invoked in `runner/agent_factory.py:160-174`, register a callback on `MessageStartEvent` (Strands) that calls `audit_sender.set_active_message_id(event.message_id)`. On `MessageStreamEvent.MessageStop` or AG-UI `TEXT_MESSAGE_END`, call `audit_sender.set_active_message_id(None)`.

### Backend-side: pass `parentMessageId` through the publish path

`src/streaming/normalize.py` / `src/api/internal.py` `_dispatch_frame` already pass through unknown fields. Verify (and add a regression test) that `parentMessageId` survives the normalize → publish → SSE serialisation pipeline. If the AG-UI client schema (`@ag-ui/client@0.0.42`) doesn't list `parentMessageId` on `TOOL_CALL_START`, augment the typed event shape in `frontend/src/lib/types.ts` to declare it (already present per the reducer's `event.parentMessageId` read at line 183).

### Frontend-side: harden the fallback

The reducer's `TOOL_CALL_START` handler at `frontend/src/lib/reducer.ts:182-219` keeps its preferred branch (use `event.parentMessageId` when present). The fallback `else` branch is tightened:

- If `parentMessageId` is missing AND there is an open assistant message (`findOpenAssistantIndex(...) !== -1`), attach to it.
- If `parentMessageId` is missing AND there is no open assistant message, the synthetic message id changes from `assistant:<toolCallId>` (which never reconciles) to a turn-stable id derived from the `runId` (`assistant:run:<runId>`), so any subsequent `TEXT_MESSAGE_START` emitted in the same run can either (a) reuse it via `ensureAssistantMessage` if the runner sends `messageId = "assistant:run:<runId>"` (it won't, in practice) or (b) we adopt the strict policy: drop the tool call if there is no parent and no open assistant message, log a `console.warn` and emit a `ReducerAction` audit so we notice in dev. We pick (b): the runner is now required to emit `parentMessageId`, so the fallback is a defensive log-and-drop, not a synthetic-attach.

This dual fix means a correct runner produces correct UI grouping via the preferred branch, and a regression in either direction (runner stops emitting `parentMessageId`, or backend strips it) surfaces as a missing tool call + a console warning rather than a silent UX corruption.

### Why not just fix the frontend fallback

Because T06 (persistence) needs `parentMessageId` to write `tool_calls` rows with the correct `parent_message_id` FK. If the runner doesn't emit it, T06 has to invent it server-side from event-stream context — feasible but couples the persister to event-ordering invariants that the runner can express directly and cheaply. Threading it through at emission time keeps the persistence layer a thin sink.

### Why not also fix `AnalystBubble.tsx`

User messages don't have tool calls. The grouping bug is exclusively assistant-side.

## Dependencies

- None blocking. T05 is independent of T01-T04.
- **T06 (tool-call history persistence) directly depends on T05.** T06 writes a `parent_message_id` FK on persisted tool calls and hydrates `MessageView.toolCalls[]` from history. The FK target is the assistant `Message.id` that T05 threads as `parentMessageId` through every emission point. Without T05, T06 must derive parent linkage from event-stream context server-side — feasible but fragile.
- T07 (markdown rendering) is independent and can land in any order relative to T05/T06.

## Notes

- **Why strict-drop on the frontend fallback instead of synthetic-attach:** the synthetic-attach behaviour today (line 193-198) makes the symptom subtle — the user just sees "weird bubble layout" with no console signal. After T05 the runner is the source of truth; a missing `parentMessageId` is a regression we want to see loudly. The `console.warn` provides a Chrome MCP-detectable signal (step 9).
- **Strands hook surface — open item:** if Strands does NOT expose a `MessageStartEvent` lifecycle hook that fires synchronously before AG-UI emission (so the setter and the emit are race-free), fall back to wrapping `agui_emit` with a closure that snoops `TEXT_MESSAGE_START` and `TEXT_MESSAGE_END` to update `_active_message_id`. Verify the timing with `docs/research/02-backend-agui.md` before implementation.
- **Webhook payload schema versioning — open item:** adding `parent_message_id` to the BeforeToolCall webhook payload is additive (backend ignores unknown fields per existing convention), but the audit-payload schema docs (if any) should mention the new optional field. T02 introduced a `tool_limit:*` reason namespace and similarly didn't bump a schema version; T05 follows the same precedent.
- **Out of scope:** retroactive grouping of already-rendered messages from PRE-T05 sessions. Old sessions in DB carry no tool calls (per T06's findings — tool events were never persisted), so there is nothing to retro-group. After T05 + T06 ship, all NEW sessions group correctly both live and on reload.
- **Why this does not require a docker image rebuild for the frontend ONLY:** the audit hook change is inside the runner image; the publish path change is inside the backend image; the reducer change is inside the frontend image. All three are independently versioned by docker-compose and the verifier rebuilds all three at step 1 to avoid any version skew.
