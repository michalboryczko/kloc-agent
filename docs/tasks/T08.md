## Spec references
- `docs/specs/agent-skills.md` — the reference doc this task realises. Decision: the runner uses `strands_agentskills` ONLY as a discovery library (YAML frontmatter validation + drop-broken-files-with-warning) and inlines each SKILL.md body verbatim into the orchestrator's system prompt at agent-build time. The Strands-native `AgentSkills` plugin (with its `skills` tool + per-skill activation telemetry) is intentionally NOT mounted; for our skill count (≤ 12) and total body (< 50 KB) the round-trip-per-activation overhead exceeds the token savings, and we want the orchestrator to internalize the skills before it issues its first MCP call.
- `runner/agent_factory.py:111-126` — the buggy site. ## Description

The orchestrator agent built in `runner/agent_factory.py:build_agent` currently sees only **skill metadata** — names + one-line descriptions — in its system prompt, because `_load_skills_prompt` delegates to `agentskills.generate_skills_prompt` which emits the Strands-native `<available_skills>` block (metadata only; bodies are gated behind the `skills` tool which we never register).

This is wrong for our deployment shape:

- Our skill count is small (≤ a dozen) and the total body weight is < 50 KB; the context-budget pressure that motivates the Strands gating doesn't apply.
- Our orchestrator's FIRST decision (decompose → retrieve → synthesise) is steered by skill content (especially `codebase-qa` + `decompose`). Gating the body behind a tool call adds a turn of latency before any real work happens — and crucially, the orchestrator must SEE the procedure before it picks a strategy.
- The `skills` tool is not registered (`AgentSkills` plugin is not mounted), so the upstream metadata-only block points the model at a tool that does not exist. The model occasionally tries to invoke `skills` and gets a tool-not-found, polluting the audit trail.

The fix is structural: keep using `agentskills.discover_skills` (it validates YAML frontmatter and silently drops broken files with a `log.warning` — a property we still want), but read each SKILL.md body ourselves and inline it into the system prompt.

We ALSO ship four new skill bodies the orchestrator needs to behave like an analyst-facing assistant:

- `biz-codebase-explorer` — persona + anti-hallucination guardrails for non-developer users (PL/EN, file:line citations mandatory).
- `codebase-qa` — three-layer procedure (decompose → retrieve → synthesize) that the orchestrator follows for any analyst question.
- `decompose` — Layer 1 mechanics (structured plan, ambiguity / adversarial / runtime-data detection).
- `kloc-mcp` — Layer 2 mechanics (kloc-intelligence MCP tool selection: which of `kloc_resolve` / `kloc_search` / `kloc_context` / `kloc_chunks` / `kloc_source` / `kloc_flows` to call when).

The existing `summarize-callgraph` skill is updated (small clarifications + a "When to escalate" / "What not to do" block; net body grows from 36 → 54 lines).

### Why not switch to the Strands-native `AgentSkills` plugin

- Activation telemetry (`plugin.get_activated_skills(agent)`) is a feature we don't need yet. Our audit signal for "did the agent use skill X" comes from the MCP-tool-call signature in `audit_log` rows (e.g. `kloc_resolve` → `kloc_search` → `kloc_context` is the `codebase-qa` fingerprint).
- The round-trip cost of "describe skill, model calls `skills` tool, tool returns body, model continues" is exactly the latency we don't want on the FIRST turn.
- The skill set is small and every turn benefits from every skill — there is no situation where "skill X is irrelevant; don't waste tokens" applies for our deployment. (`agent-skills.md` documents the criteria under which migration would be worthwhile; none currently hold.)

### Inlining contract (the exact prompt shape)

After this task, every runner spawn's `system_prompt` ends with:

```
<available_skills>
The following skills are inlined in full. Treat each one as if you had
already read it — do NOT issue a file_read just to load a SKILL.md
whose body is already shown below. Apply the skill when its description
matches the user's question.

<skill>
  <name>biz-codebase-explorer</name>
  <description>Persona + guardrails for answering business-analyst-style questions ...</description>
  <body>
# Biz Codebase Explorer (persona)

You are **biz-codebase-explorer** — a senior code analyst that translates ...

## Mission

[...full body...]
  </body>
</skill>

<skill>
  <name>codebase-qa</name>
  <description>End-to-end workflow for answering business-analyst questions...</description>
  <body>
[...full body...]
  </body>
</skill>

[...one block per discovered skill, in stable filesystem order...]
</available_skills>
```

The `<body>` content is the SKILL.md file MINUS the leading `---…---` frontmatter block (which would re-emit name + description redundantly). Whitespace inside `<body>` is preserved verbatim so the procedural steps line up.

## Deliverables

1. **`runner/agent_factory.py`** — replace `_load_skills_prompt` (lines 111-126) with a manual-inlining loader. Pseudocode:

   ```python
   def _load_skills_prompt(skills_dir: Path) -> str:
       try:
           from agentskills import discover_skills  # type: ignore
       except ImportError:
           log.warning("skills.agentskills_not_installed; skipping skills prompt")
           return ""
       try:
           skills = discover_skills(skills_dir)
       except Exception:
           log.exception("skills.discover_failed", extra={"dir": str(skills_dir)})
           return ""
       if not skills:
           return ""

       header = (
           "<available_skills>\n"
           "The following skills are inlined in full. Treat each one as if you had\n"
           "already read it — do NOT issue a file_read just to load a SKILL.md\n"
           "whose body is already shown below. Apply the skill when its description\n"
           "matches the user's question.\n"
       )
       blocks: list[str] = []
       for skill in skills:
           try:
               raw = Path(skill.path).read_text(encoding="utf-8")
           except OSError:
               log.warning("skills.body_read_failed", extra={"path": skill.path})
               continue
           body = _strip_frontmatter(raw)
           blocks.append(
               f"<skill>\n  <name>{skill.name}</name>\n"
               f"  <description>{skill.description}</description>\n"
               f"  <body>\n{body}\n  </body>\n</skill>"
           )
       if not blocks:
           return ""
       return header + "\n" + "\n\n".join(blocks) + "\n</available_skills>"


   def _strip_frontmatter(raw: str) -> str:
       """Strip leading `---\\n…\\n---\\n` block, returning the SKILL body.
       If the file has no frontmatter (no leading `---`), return raw unchanged."""
       if not raw.startswith("---"):
           return raw
       parts = raw.split("---", 2)
       if len(parts) < 3:
           return raw
       return parts[2].lstrip("\n")
   ```

## Notes
- **Why ship four new skills now, not one at a time.** `codebase-qa` references `decompose` and `kloc-mcp` and `biz-codebase-explorer`; landing one without the others leaves dangling references in the prompt and the orchestrator gets confused about which procedure to follow. The bodies are small and the spec presents them as a coherent set.
- **The discoverer's silent-drop-on-broken-frontmatter property is preserved.** The dev MUST keep using `agentskills.discover_skills` (rather than walking the directory directly) precisely so a malformed YAML frontmatter file produces a `log.warning` and is skipped — matching the operator expectation already documented at `runner/agents_loader.py:6`. The verifier's step 5 (unit test) covers this.
- **Migration to the plugin pattern.** `docs/specs/agent-skills.md` § "When to switch to the plugin pattern" lists the four criteria (skill count > ~20, situational skills, telemetry need, resource-file fetches). None of these hold today; revisit when they do.
- **Observability gap is documented, not closed.** No new audit event names. Skill application is inferred from MCP-tool-call signature (e.g. `codebase-qa`'s fingerprint is `kloc_resolve` → `kloc_search` → `kloc_context` → `kloc_source`). A first-class "which skills did this session activate?" signal lands when/if we adopt the plugin pattern.
- **Subagents are untouched.** `runner/agents_loader.py` keeps its tool-based exposure (one tool per `agents/<name>/AGENT.md`). The symmetry the docstring promises (one loader pattern across `/skills` and `/agents`) becomes: same discoverer-shape, divergent activation (skills inlined vs subagents tool-exposed). The composition.xml note documents this.
