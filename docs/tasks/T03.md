# T03 — fix-runner-startup-heartbeat-race: first-heartbeat budget too tight for cold-start MCP init

## Status
- passed-infra-skipped

## Description

Cold-start runner spawns die before producing any visible answer because the heartbeat watcher fires before the runner's first scheduled heartbeat lands. The flow:

1. `RunnerRegistry.get_or_spawn` calls `runner.spawn(handle)`. The Docker container starts; spawn returns as soon as Docker reports the container is running. The Python process inside has not yet imported `runner.__main__`.
2. `HeartbeatWatcher.start()` runs immediately after spawn returns. The 30 s clock starts.
3. The runner's Python process boots, reads hydration, opens MCP clients against `host.docker.internal:8765` (kloc-intelligence), discovers skills, registers audit hooks, builds the Strands agent. Under a moderately loaded host this routinely takes 15–40 s.
4. `BackendChannel.start()` is called at the end of init. `_heartbeat_loop` begins with `await asyncio.sleep(HEARTBEAT_INTERVAL_S)` — 15 s — before the first emit.
5. If steps 3 + the 15 s sleep total more than 30 s, the watcher fires first: `runner_heartbeat_lost` audit row, container terminated, the in-flight POST `/stream` hangs until the `stream.persister_idle_timeout` (60 s budget) closes the SSE stream with no terminal frame. From the analyst's seat: send → spinner → nothing.

The runner *does* emit a `runner_ready` frame as the very first thing on `channel.start()`, *before* the heartbeat loop sleeps. The backend's JSONL ingress receives it but treats it as a no-op (it has no `runId` and no AG-UI bus topic). The dispatch table at `src/api/internal.py:109` only matches `"heartbeat"` and `"RunnerHeartbeat"` for the beat-reset path. Widening that set to include `runner_ready` makes the existing first-frame *also* be the first beat — the runner is already advertising "I'm alive, channel is open" at the right moment; the backend just isn't listening.

Three layered changes are required because each one alone is insufficient:

- **(a) Backend dispatch.** `runner_ready` joins the heartbeat-reset frame set in `src/api/internal.py`. The watcher resets the moment the channel comes online, not 15 s later. This is the core fix.
- **(b) Runner first-beat.** `_heartbeat_loop` emits the first `type: "heartbeat"` frame immediately, then enters the existing `await sleep → emit` loop. Belt-and-braces: even if a future change strips `runner_ready` from the dispatch set, the runner still produces a beat at t≈0.
- **(c) Default timeout.** `runner_heartbeat_timeout_s` default rises from 30 → 60. The 30 s cap was set when runners had no MCP dependency; the kloc-intelligence MCP handshake plus Strands+skills build is the slow path now, and 30 s leaves no margin. 60 s still detects a hung runner within one warm-idle countdown.

### Observability

A new OTel histogram `kloc_agent.runner.spawn_to_first_beat_s` is emitted from the ingress on the *first* beat-equivalent frame for a session (whichever of `runner_ready` / `heartbeat` arrives first). Buckets `{1, 2, 5, 10, 15, 30, 60}` seconds. This gives operators a quick read on whether MCP init is regressing on the host without having to grep logs.

No new audit event vocabulary. `runner_heartbeat_lost` remains the only audit row for this failure mode.

## Deliverables

1. **`src/api/internal.py`** — `_dispatch_frame` widens the heartbeat-reset frame set:
   ```python
   if frame_type in ("heartbeat", "RunnerHeartbeat", "runner_ready"):
       on_hb = getattr(registry, "on_heartbeat_frame", None) if registry else None
       ...
   ```
   The existing `return` path stays. `runner_ready` is *also* not published to the bus (it has no AG-UI semantics for the FE). The OTel histogram `kloc_agent.runner.spawn_to_first_beat_s` is recorded here on the first beat-equivalent frame seen for a session — tracking the first-seen timestamp in a process-local `dict[str, float]` keyed by session_id, populated on `runner_spawned` audit emission and consumed on first beat.

2. **`runner/channel.py`** — `_heartbeat_loop` is restructured so the first emit happens at t≈0:
   ```python
   async def _heartbeat_loop(self) -> None:
       while True:
           await self.emit({
               "type": "heartbeat",
               "session_id": self._session_id,
               "runner_id": self._runner_id,
               "ts": int(time.time() * 1000),
               "busy": self._busy,
           })
           try:
               await asyncio.sleep(HEARTBEAT_INTERVAL_S)
           except asyncio.CancelledError:
               return
   ```
   Behaviour change: one extra `heartbeat` frame per runner lifetime, at startup. Cost is negligible (the frame is ~165 B). The cancel-during-sleep semantics are preserved.

3. **`src/settings.py`** — `runner_heartbeat_timeout_s: int = 60` (was `30`). Inline comment notes that the default is sized to clear cold MCP init on a moderately loaded host; reduce only when the host is known idle.

4. **`.env`** + **`.env.example`** — `RUNNER_HEARTBEAT_TIMEOUT_S` default value updated to `60` in both files. The accompanying comment explains the cold-start budget.

5. **`src/runner_mgmt/heartbeat.py`** — module-level docstring updated to record that `runner_ready` resets the watcher. No code change.

6. **`docs/usdl/composition.xml`**:
   - Update the rule at line ~179 from `Heartbeat reset is driven only by 'type: "heartbeat"' / 'RunnerHeartbeat' frames on the JSONL ingress; AG-UI events do not reset the watcher.` to `Heartbeat reset is driven by 'type: "heartbeat"' / 'RunnerHeartbeat' / 'runner_ready' frames on the JSONL ingress; other AG-UI events do not reset the watcher. 'runner_ready' is the runner's first emitted frame and counts as the cold-start beat.`

The `runner_ready` frame is the de-facto first beat at the ingress level; the explicit `heartbeat` frame follows promptly."*

7. **`docs/usdl/interfaces.xml`** — `ifc.ingest-runner-events` intent (line ~298): append a sentence naming `runner_ready` as a beat-equivalent frame so the contract surface matches the dispatch behaviour.

## Notes

- The `runner_ready` frame already exists and is already sent at exactly the right moment; the backend just isn't using the signal. This is why the fix is small and high-confidence.
- The 60 s default is conservative. If `kloc_agent.runner.spawn_to_first_beat_s` consistently reports values < 5 s in production telemetry, a follow-up can tighten it. Do not tighten it without that data.
- The injected-delay test fixture (`INJECT_RUNNER_INIT_DELAY_S`) is the only runtime env read added to the runner image. It is read once at the top of `runner/__main__.py`, behind an `if` guard, and is a no-op when unset. This is acceptable because the runner is not bound by `con.settings-no-runtime-env-reads` — that constraint is scoped to the backend, where `Settings` is the single source. The runner reads its hydration JSON for everything else.
- A future task may also send a richer first-beat payload (e.g. include `mcp_init_ms`, `agent_build_ms`) so operators can drill into *which* part of cold-start is slow when telemetry shows regressions. Out of scope for T03; tracked as an open item.
