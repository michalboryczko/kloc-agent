## Description

Assistant responses produced by the orchestrator routinely contain markdown — `**bold**`, `# Headings`, `- bullets`, fenced ` ```code``` ` blocks, inline `` `code` ``, occasionally tables. The UI currently renders those tokens as literal characters because `AssistantBubble.tsx` inserts `{message.content}` as a JSX text node into a `<p>` with `whitespace-pre-wrap`. The reference design shows inline code as a styled pill and prose as proper typography; the bug is the missing render step.

T07 wires `react-markdown` into the assistant bubble with `remark-gfm` for GFM extensions. The renderer is constrained to a safe subset by:
- **Not enabling `rehype-raw`** — raw `<script>`/`<iframe>` tags in markdown stay escaped as text.
- **Custom component overrides** that style the output with our Tailwind tokens and constrain link `target`/`rel`.
- **`urlTransform`** that strips `javascript:` and `data:` (other than `data:image/`) schemes from links.

### Scope of markdown rendering

Render everything `react-markdown` + `remark-gfm` supports by default, with custom Tailwind component renderers:

| element | renderer |
|---|---|
| inline code (`` `code` ``) | `<code class="px-1 py-0.5 mx-0.5 rounded bg-[var(--color-chip-bg)] text-[var(--color-chip-fg)] mono text-[12.5px]">` |
| fenced code (` ```lang ` blocks) | `<pre class="my-3 p-3 rounded bg-[var(--color-chip-bg)] overflow-x-auto"><code class="mono text-[12.5px] leading-[1.55]">...</code></pre>`. No syntax highlighting in v1 — picks the right surface but defers `shiki`/`highlight.js` to a follow-up. |
| paragraphs | `<p class="text-[14px] leading-[1.65] mt-3 mb-3 break-words">`. Note: `whitespace-pre-wrap` is REMOVED — markdown's whitespace semantics replace pre-wrap behaviour, and pre-wrap interacts badly with `react-markdown`'s output. |
| h1 / h2 / h3 / h4 | scaled headings using the existing typography tokens (`text-[18px]/[16px]/[14px]` font-weight 600, modest top margin). |
| ul / ol | indented lists with our existing list-style; small `gap-y` between items. |
| li | inherits list parent. |
| blockquote | `<blockquote class="border-l-2 border-[var(--color-chip-bg)] pl-3 my-3 italic">` |
| tables (GFM) | `<table class="w-full text-[13px] my-3 border-collapse">` with `th`/`td` border-bottom + padding. Overflow contained in a wrapper div with `overflow-x-auto`. |
| links | `<a target="_blank" rel="noopener noreferrer nofollow" class="underline text-[var(--color-accent)]">`. URL is run through `urlTransform`. |
| images | rendered with `<img loading="lazy" class="my-3 max-w-full rounded">`. Markdown image attacks (e.g. `data:` URIs) are filtered by `urlTransform`. |
| hr | `<hr class="my-4 border-[var(--color-chip-bg)]">` |
| del (GFM strikethrough) | `<del class="opacity-70">` |
| task list checkboxes (GFM) | rendered as disabled inputs via the default `react-markdown` behaviour. |
| html (raw) | DISABLED (no `rehype-raw`). Raw HTML in the markdown source renders as escaped text. |

### Streaming compatibility

The renderer runs against the accumulated `message.content` string on every render pass (every `TEXT_MESSAGE_CONTENT` event triggers a state update which re-renders). React reconciles the DOM tree efficiently; markdown is parsed on each pass but the strings involved are tiny (a single assistant turn rarely exceeds ~10 KB). If profiling shows perf issues at very long messages, memoise with `useMemo(() => <ReactMarkdown>{message.content}</ReactMarkdown>, [message.content])` keyed off the content string — left as a follow-up unless step 12 (frontend lint + typecheck) surfaces a render-time warning.

The blinking caret (`<BlinkingCaret />`) is appended OUTSIDE the markdown tree, as a sibling element, so half-typed `**bo` shows the caret immediately after the literal `**bo` text without trying to interpret a half-open bold token mid-stream. When the next delta completes `**bold**`, react-markdown re-parses and renders the styled span. The transient half-token flicker is acceptable and matches ChatGPT / Claude.ai behaviour during streaming.

### Why not `markdown-it` / `marked`

- `react-markdown` is the React-native choice; it returns a React tree, so component overrides slot in cleanly with our existing Tailwind classes and CSS-vars.
- `markdown-it` returns HTML strings that we'd need to `dangerouslySetInnerHTML` (or pipe through `rehype-raw`, defeating the safe-default posture).
- `marked` is older and lacks ergonomic React bindings.

### Why not also touch `AnalystBubble.tsx`

- Users type questions, not formatted documents. The spec image shows the user's question as plain prose.
- Rendering markdown in the user bubble enables a confused-deputy XSS surface (a user pasting `[click](javascript:...)` into their OWN bubble doesn't escalate, but it's a noisy UX inconsistency).
- If a future use case demands user-side markdown, that's a follow-up.

### Why `isomorphic-dompurify` if we're not enabling raw HTML

Defense in depth. `react-markdown` v9+ does not pipe raw HTML by default (`rehype-raw` is opt-in). If a future change accidentally enables it, having DOMPurify in the dep tree means we can drop in `rehype-sanitize` or a custom rehype plugin wired to DOMPurify without a new dep install. Cost: ~50 KB gz. Worth it for the safety property and the trivially-discoverable lever.

   import ReactMarkdown, { type Components } from "react-markdown";
   import remarkGfm from "remark-gfm";

   const SAFE_URL = /^(https?:|mailto:|tel:|#|\/|\.)/i;
   const SAFE_IMAGE = /^(https?:|data:image\/)/i;

   function urlTransform(url: string) {
     return SAFE_URL.test(url) ? url : "#";
   }
   function imageTransform(url: string) {
     return SAFE_IMAGE.test(url) ? url : "";
   }

   const components: Components = {
     a: ({ href, children, ...rest }) => (
       <a
         {...rest}
         href={href}
         target="_blank"
         rel="noopener noreferrer nofollow"
         className="underline text-[var(--color-accent)] break-words"
       >
         {children}
       </a>
     ),
     code: ({ inline, className, children, ...rest }) =>
       inline ? (
         <code
           {...rest}
           className="px-1 py-0.5 mx-0.5 rounded bg-[var(--color-chip-bg)] text-[var(--color-chip-fg)] mono text-[12.5px]"
         >
           {children}
         </code>
       ) : (
         <code {...rest} className={`${className ?? ""} mono text-[12.5px] leading-[1.55]`}>
           {children}
         </code>
       ),
     pre: ({ children, ...rest }) => (
       <pre {...rest} className="my-3 p-3 rounded bg-[var(--color-chip-bg)] overflow-x-auto">
         {children}
       </pre>
     ),
     p: ({ children, ...rest }) => (
       <p {...rest} className="text-[14px] leading-[1.65] mt-3 mb-3 break-words">
         {children}
       </p>
     ),
     ul: ({ children, ...rest }) => (
       <ul {...rest} className="list-disc pl-5 my-2 space-y-1 text-[14px] leading-[1.65]">
         {children}
       </ul>
     ),
     ol: ({ children, ...rest }) => (
       <ol {...rest} className="list-decimal pl-5 my-2 space-y-1 text-[14px] leading-[1.65]">
         {children}
       </ol>
     ),
     h1: ({ children, ...rest }) => (

## Notes

- **Why not syntax-highlight code blocks today:** `shiki` adds ~600 KB raw / ~180 KB gz to the bundle (loaded on demand, but still meaningful for first-paint). The MVP UX value of "code blocks are visually distinct" is captured by the `<pre><code>` styling alone; chroma colors are a nice-to-have. Tracked as a follow-up.
- **`urlTransform` decision — open item:** the default `react-markdown` URL transformer (v9) already filters `javascript:` and `vbscript:` schemes. Our custom `urlTransform` is stricter (whitelist-based instead of blacklist). Open question: do we want to allow `data:image/*` for inline images? The default `imageTransform` permits it — this is intentional because the AG-UI server may emit data-URI thumbnails for small artifacts. We do NOT allow `data:` for `<a>` (covered by `urlTransform`).
- **Memoisation deferred:** `MarkdownContent` is re-evaluated on every state update during streaming. For typical messages (<10 KB) this is fast. Profile and add `useMemo` only if Chrome DevTools React Profiler shows it as a hot path.
- **User-bubble markdown deferred:** keeping `AnalystBubble.tsx` as plain text is a UX decision, not a technical limitation. Re-evaluate if/when analysts demonstrate a need (e.g. pasting a structured code snippet into the prompt input and expecting it to render formatted).
- **Why ship `isomorphic-dompurify` even though we don't import it:** see Description. It's a 50 KB safety lever for future raw-HTML-enabling changes. If post-T07 review prefers strict-as-shipped, drop the dep and the lever; the rest of T07 still ships safe.
- **`whitespace-pre-wrap` removal is deliberate:** with markdown rendering, single newlines collapse to spaces per markdown semantics, and double-newlines start a new paragraph. This matches author intent for LLM output far better than pre-wrap, which preserved arbitrary whitespace as-is (and made markdown look "intentional but ugly").
